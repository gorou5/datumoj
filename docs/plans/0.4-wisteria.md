## 1. 一句话

在 DATUMOJ 里加一个子系统 **Eltiro**（提取）：外部项目把"要什么数据"注入进来，Eltiro 读懂资料库里已有的内容，把需求匹配到具体的数据上，按固定的数据代次取数、对齐、计算，交出带出处的结果；资料库增长以后，Eltiro 自己把新数据匹配到已有的需求上。

## 3. 为什么做这些

### 3.1 需求从哪里来
需求例子是三个页面，以后会持续更新：
- https://plan.datumoj.com/ （总览）
- https://plan.datumoj.com/verify/ ：30 个单源数据失真验证案例。每例假设某国某项数据失真，用 3 个以上独立来源交叉核对（镜像法、实物量锚点、卫星复核、存量反推、统计指纹）。
- https://plan.datumoj.com/cases/ ：100 个多源融合分析案例。每例至少 3 个来源，拼起来回答单看一个来源答不了的问题。

### 3.2 读完这 130 个案例得到的结论（2026-10-24）
1. **几乎都是结构化序列**：要的是"某国 × 某指标 × 某段时间"的数值，再在几个来源之间对齐、相减、求比值、做残差。文本只在少数案例里用到（如官方通报、修订说明）。
2. **来源以国际组织为主**：IMF、世界银行、OECD、联合国各机构（UNSD、FAO、WHO、UNICEF、UNESCO、ILO、UNODC 等）、BIS、UN COMTRADE、Copernicus/ESA，以及各国统计局。**日本的数据只出现在 3 个案例里**（#079 国家综合统计、#098 长期时间序列、V13 每月勤劳统计）。逐例的来源和可得程度见附表 `docs/plans/0.4-wisteria-cases.md`：WISTERIA 之后全部来源可得的只有 4 例，69 例一个来源都没有计划。
3. **现有资料库几乎覆盖不到**：Rikolto 目前只有日本政府数据，0.3 加上 Eurostat 和世界银行 WDI。所以对大部分案例，Eltiro 第一次匹配的结果会是"缺什么数据"。**缺口报告本身就是重要产出**：它告诉 Rikolto 下一步该接哪些来源。
4. **有些案例要修订历史**：希腊赤字修订链（V07）、印度 GDP 回算（V09）、日本工资统计重算（V13）都要比较同一指标的多次发布。Rikolto 按快照保留历史，这是优势，但观测值库现在只能查当前版本，要补"按发布时间查"（契约 002）。
5. **有些不在可做范围**：卫星栅格（夜光、Sentinel）、答题卡擦改率、选区级投票这类微观或遥感数据，本版本不做（第 5 节）。

### 3.3 已定的原则（2026-10-24）
- Eltiro 放在 DATUMOJ 里，作为服务提供方；外部项目通过**注入需求定义**来取数据。
- **有使用条款限制的数据，输出只能是最终结果，原始物不流出**。把受限数据发给云端模型也算流出。
- **模型是可选项**：按难度用不同的模型，本地或云端按配置选；不配模型也能跑，只是需要理解文本的步骤交给人。
- 需求定义跟不上数据增长，系统要自己匹配。
- **原始物与最终结果的界线**（2026-10-24）：原始物指 raw 文件、原文和文本片段；经过 Eltiro 整理的数值（对齐、规范化、运算后的序列）是分析结果，不算原始物，即使某个值和来源原值相同。
- **改名全部改**（2026-10-24）：文档、命令、MCP 名称和代码模块路径都改成 Rikolto。2026-10-26 起改名在 MAPLE 做（MAPLE 119），本版本不动。
- **本地开发默认用 Claude 套餐**（2026-10-24）：本机开发和运行时，模型档位默认走 Claude 订阅套餐（Claude Code 的无头调用），不需要 API Key；本地 Ollama 和其他提供方按配置可选。
- 沿用 Rikolto 的规则：数值只从 SQL 取，不让模型估数；不同调查的数据不直接相加；口径、单位原样记录，不自行换算。

## 4. 目标（WISTERIA 完成的标准）

0. **契约**（检查点 m0）：Eltiro 的契约（需求定义、序列登记、匹配记录、输出包、许可等级、模型路由）和观测值按发布时间查询的契约经人审查。
1. **需求注入**：外部项目用一个声明式文件提交需求（用途、实体、指标说明、时间范围、输出字段、运算、正反例），Eltiro 校验后登记；不接受可执行代码；每个外部项目有自己的身份、可用来源、可用模型和预算，所有运行留审计记录。
2. **读懂已有数据**：Eltiro 为资料库里的每个序列（观测值表的指标）、目录数据集和文档簇维护一份画像：概念、单位、口径、地区和时间覆盖、频率、来源、许可、发布次数；按新代次和变化记录增量更新。每个画像区分三种可得程度：数值已入库、只在目录里看到、没有。
3. **匹配**：把需求里的每个指标匹配到序列上，先用确定性方法（代码表、概念编号、关键词），再用向量召回，最后可选模型判断；每条匹配记下理由、置信度和依据；低置信度进人工确认队列；人确认或否决的结果会被记住。
4. **增量重匹配与提醒**：每出一个新代次，变化的序列反过来匹配所有在用的需求；已绑定的序列停更、口径变化、出现更好的候选时提醒。
5. **执行与输出**：需求按固定代次运行；取数只走 SQL；地区码、时间对齐；运算只用固定的运算库（差、比、增长率、镜像差、相对基准的残差、领先滞后相关等），换算必须是显式运算并记录换算依据；输出包含数据文件、清单（需求版本、数据代次、使用的模型）、逐行出处、许可汇总、与上次运行的差异。
6. **许可闸门**：每个来源有许可等级（可输出原始值 / 只能输出派生结果 / 不得流出）和"能否送云端模型"标记；只能输出派生结果的来源，输出里不出现原始数值、原文和片段；闸门在输出写出前检查，不通过整包不交出。
7. **缺口报告**：需求要的数据库里没有（或只在目录里）时，列出缺什么、可能的来源，作为 Rikolto 来源计划的输入。
8. **试点**：4 个案例（第 6.8 节，2026-10-24 定）做成需求，从注入到输出端到端跑通；为它们接入所需的国际来源。
9. **评测**：试点需求的标准匹配答案；匹配的查准率、查全率，输出数值与来源原值的核对；和 IVY、TACHIBANA、MAPLE 的题一起全部达标。
10. **真实验收**：模拟一个外部项目注入试点需求，拿到输出；人逐项核对数值、出处和许可闸门，记录到 `docs/acceptance/v0.4.0-wisteria.md`。

## 5. 不做

- **Purigo（数据保留和删除）**：仍不做。
- **卫星栅格和微观数据**：夜光、Sentinel 遥感、答题卡、选区级投票等；需要时以后用已经汇总好的公开产品（如按行政区汇总的夜光序列）作为普通序列接入。
- **执行外部项目提交的代码**：需求只能是声明式的；运算库之外的统计建模（回归模型、因果推断）由外部项目在拿到结果后自己做。
- **对外公开的 HTTP 服务**：本版本的注入入口是本机的文件和命令行；网络接口以后再定。
- **直接抓取被排除国家的统计局**（中、俄、土、印，`docs/PLAN.md` 第 3 节）：这些国家的数据只通过国际组织的序列取得。
- **自动换算货币和口径**：只在需求里显式写了换算运算、且换算依据（汇率序列等）本身也来自资料库时才做。
- **主动推送**：提醒和缺口报告仍只在命令行、管理页面和报告文件里。

## 6. 设计

### 6.1 需求定义（注入）
- 一份需求是一个 YAML/JSON 文件，按 JSON Schema 校验：`id`、`consumer`、`version`、用途说明、实体（国家用 ISO 3166 代码，地区用对应代码表）、指标（用文字描述概念，可附偏好来源，**不写死表名**）、时间范围和频率、对齐键、运算、输出字段、正例和反例、可接受的许可等级、允许的模型档位和预算。
- 样例：`docs/plans/0.4-wisteria-samples/` 下两个文件（模拟外部项目的两份需求，取自试点 #002 和 V07，一份需求一个文件）；来源 id 用注册表的写法（`intl-imf-weo`、`intl-oecd`、`intl-wdi`、`eu-eurostat`）；契约 001 的 schema 以它为基准，字段可以改，但它表达的内容都要能表达。
- 注入入口：放进使用方的收件目录，或用命令提交；结果写到使用方的发件目录。
- 外部注入的定义是**信任边界**：严格校验、大小和复杂度上限、拒绝未知字段、运行资源上限、按使用方限定可用来源和模型；需求文本只当数据，不执行其中任何指令（同 Rikolto 对来源内容的规则）。

### 6.2 序列登记（内容画像）
- 从观测值库（表、指标、单位、口径、地区、时间）、目录（数据集元数据）、文档块（主题聚类）生成画像，存进 Eltiro 自己的库，不改 Rikolto 的库。
- 按代次增量：只处理变化记录里新增或修改的部分；画像带生成它的代次号。
- 概念归一：优先用来源自带的编号（SDMX 概念、WDI 指标代码、e-Stat 表号），再用多语言名称和说明；可选模型生成一句话概念说明，标注是模型生成的。

### 6.3 匹配
- 三档：确定性（代码、编号、关键词）→ 向量召回 → 可选模型判断（按难度和配置选档）。每档都可关闭。
- 匹配记录：需求指标、序列、档位、置信度、理由、依据（画像条目和出处）、数据代次、人工确认状态。人确认的绑定在后续运行中优先使用；被否决的不再推荐。
- 口径保护：概念相同但口径、单位、调查不同的序列不能自动合并，只能作为候选让人选。

### 6.4 增量重匹配与提醒
- 新代次出来后，取变化的序列，用反向索引找到可能相关的在用需求，只对这些重新匹配。
- 提醒：已绑定序列停更（超过其频率未更新）、口径或单位变化、出现置信度更高的新候选、需求要的数据从"缺"变成"有"。

### 6.5 执行与输出
- 每次运行开始时取定一个已发布的数据代次，记下它的 `generation_token`；之后每次只读 SQL 都带上并校验这个 token，只读该代次的快照，运行中出了新代次也不切换。token 无效或代次不可用就停止，不回退到最新代次，不交出输出。
- 每个输入观测值保留完整身份：`(source_id, table_key, obs_id)`、`snapshot_sha256` 和发布标识（002 定义）；不只按 `obs_id` 关联或去重，解析不唯一就报错。数据代次和来源发布是两回事：修订对比是在同一个代次里查多次发布。
- 运算库：对齐（地区码、日历）、数量级换算（倍率取自来源元数据并记录依据，倍率未确认就不算）、差、滞后差、比、增长率、来源间离散度（各来源与中位数的差）、修订差（相对首次发布）、镜像差、相对基准的残差、移动平均、领先滞后相关；每个运算记录输入和参数。
- 输出包：数据文件（Parquet，附 CSV）、`manifest.json`（需求 id 与版本、数据代次和 `generation_token`、运行时间、使用的模型和档位、许可汇总）、逐行出处、缺口报告、与上次运行的差异。逐行出处带所有输入的完整身份和运算链；只给引用编号时，包内的出处索引要能解析到这些信息，不附原文。

### 6.6 许可闸门
- 许可等级放在现有的 `LicenseInfo`（`sources/*.yaml` 的 `license`）里，加 `outflow`（`raw_ok`、`derived_only`、`no_outflow`）和 `cloud_model_ok`，缺省 `no_outflow` / `false`。注册表校验过的 `LicenseInfo` 是唯一权威：画像、输出清单、缓存里的副本不能覆盖它，使用方配置只能再收紧。
- 旧记录迁移（102）：`usage_scope=redistributable` 且 `redistribution=allowed` 映射为 `raw_ok`，其余（`internal_only`、`forbidden`、`unverified`）一律 `no_outflow`；`cloud_model_ok` 一律先设 `false`。`derived_only` 和 `cloud_model_ok=true` 只能由 H2 按条款核准，记下许可名称、官方 URL、核对日期和依据，不从旧字段推断。旧字段保留为由新字段推出的兼容值，两者矛盾的记录注册表直接拒绝。102 完成后 805、806 才能开工。
- `derived_only` 的来源：输出可以有整理过的数值（对齐、规范化、运算后的序列），不能有 raw 文件、原文和文本片段；出处只给引用编号，不附原文。`no_outflow` 的来源：不能进任何输出，只能用于匹配和内部校验。
- 闸门在输出写出前逐列检查数据血缘，不通过就整包不交出并说明原因。
- 界线按第 3.3 节：整理过的数值算最终结果，raw 文件、原文、片段算原始物。

### 6.7 模型路由
- 一个配置文件把"步骤 × 难度"映射到提供方：`none`、Claude 套餐（本地开发的默认，通过 Claude Code 无头调用，按难度选模型）、本地 Ollama、云端 API。凭证只从环境变量读，不进仓库。
- Claude 套餐用于这类自动调用是否符合 Anthropic 的条款，H0 先核对并记下官方页面和核对日期；不符合的场景改用 API 或本地模型。无人值守的环境（NAS）能不能用套餐、能不能在 NAS 上跑本地模型，NAS 到货后按硬件和条款再定；本版本的模型调用先只在本机跑。
- Claude 套餐和云端 API 都算云端模型：`no_outflow` 的数据不进云端模型，即使 `cloud_model_ok` 为真；`cloud_model_ok` 为否的来源只能走本地 Ollama 或 `none`。混合来源的输入在构造提示词之前按许可拆开，分别路由；拆不开就进人工队列，不调用模型。
- 路由在运行开始前选定：受使用方允许的档位、来源许可和预算约束，不满足就降档，降到 `none` 就进人工队列。选定的提供方、模型及版本、路由策略写进运行记录；运行中（包括重试）不换，不可用就让这次运行失败。
- 模型输出按"使用方 + 授权来源范围 + `generation_token` + 输入哈希 + 提供方 + 模型及版本 + 路由策略哈希 + 提示词版本"缓存。同一代次重跑复用原来的路由和缓存，缺了就失败；读缓存前重新校验许可和授权，对不上就不复用。输出记录每个字段由哪个提供方、模型和档位产生。
- 003、806 的测试必须覆盖：`no_outflow` 不进云端模型；混合来源拆分或进人工队列；不同使用方的缓存隔离；授权、代次或路由策略变了不复用旧缓存。

### 6.8 试点案例（2026-10-24 定）
挑需要的来源少、数据是结构化接口、能覆盖不同运算的 4 个：

| 案例 | 用到的来源 | 覆盖的能力 |
|---|---|---|

### 6.9 Rikolto 本版本的配合
- **改名**：已移到 MAPLE（MAPLE 119，2026-10-26），本版本不改名；Rikolto 的模块在 `datumoj.rikolto`，Eltiro 的代码放 `datumoj.eltiro`。
- **观测值按发布时间查询**（契约 002 + 实现）：同一序列的历次发布都保留，`query_sql` 可以按"截至某次发布"查询。
- **历史发布补取**：Rikolto 的快照只从开始抓取那天起才有，V07 要的 2009—2010 年历次发布不在库里。301 支持导入来源公开的历史版本存档（Eurostat 历次 EDP 通报、IMF WEO 历史版本），每次发布带发布标识和发布日期；存档能否取得、许可如何，由 H2 核验，H4 抽查数值和原存档一致。
- **国际来源**：按试点需要接入 IMF、OECD、ILO、UN COMTRADE、WTO（WTO 接入为 306，接口和范围由 H2 核验定稿）；优先用 SDMX 等标准接口，用现有 HTTP 客户端，不为几行代码加库。H2 没核验完许可和配额的来源不启用。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 匹配错把口径不同的序列当成同一个 | 口径、单位、调查不同只做候选不自动合并；标准答案评测；人工确认队列 |
| 受限数据经输出或云端模型流出 | 许可闸门按数据血缘检查；`cloud_model_ok` 缺省为否；许可闸门的反例进评测 |
| 外部注入的需求被用来越权取数或注入指令 | 声明式定义、严格校验、按使用方限权、需求文本只当数据、审计记录 |
| 模型费用和结果不稳定 | 按难度分档、预算上限、缓存；不配模型也能跑 |
| 需求页面频繁更新，需求定义跟不上 | 页面变化转成草稿等人确认；已登记的需求有版本号 |
| 国际来源接口各异、需要 Key、有配额 | 优先 SDMX 标准接口；Key 只从环境变量读；按试点需要逐个接 |
| 修订历史让观测值库变大 | 只对需要的序列保留历次发布；体积写进每周报告 |
| MAPLE 还没进 `main`，两个版本一起压在特性分支上 | `feature/0.4` 从 `feature/0.3` 建，不再往 `feature/0.3` 写代码，MAPLE 剩下的任务也合进 `feature/0.4`；MAPLE 的运维步骤（NAS 一周试运行、验收）不改代码；向 `main` 的 PR 顺序另定 |
