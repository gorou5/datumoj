# DATUMOJ 0.3（代号 MAPLE，楓）计划

> 草案 v0.1（2026-10-22）。总计划见 `docs/PLAN.md`，版本规则见其第 8 节。0.2（TACHIBANA）的计划见 `docs/plans/0.2-tachibana.md`。
> 任务编号 `DATUMOJ-MAPLE-<序号>`，号段沿用开发线：契约修订 001–009，A 线 1xx，B 线 2xx，C 线 3xx，D 线 4xx，E 线 5xx，F 线 6xx，G 线 7xx，集成 9xx。

## 0. 流程

与 TACHIBANA 相同（`docs/plans/0.2-tachibana.md` 第 0 节）：计划 PR → 任务 PR → 从最新的 `main` 建 `feature/0.3` 开发 → 验收后向 `main` 提 PR → 在 `main` 上打 tag（`v0.3.0-maple`，检查点 `-m<N>`）。计划文件只出现在计划和任务的 PR 里；节点完成时更新 `plan/milestones.json`。

## 1. 一句话

让资料库**在 GitHub Actions 上按来源定时自己更新**，原始文件和索引都放在 R2，本机随时可以拉下来用；同时把来源扩到**欧美**和几类日本统计数据。

## 2. 为什么做这些

- **持续更新离不开云端运行**：0.2 的抓取都在本机跑，机器休眠或关机就中断；气象厅的 feed 只保留约 7 天，断几天就永久缺数据。R2 凭证只放在 GitHub Actions 的 secrets 里（2026-10-22），所以运行环境定为 Actions。
- **ADR 0002 已定但没实现**：索引跟随数据上 R2，本机的库和索引是可以按需从 R2 重建的工作副本；同步频率按来源分别设置。
- **0.2 留下的观察**：新来源的一周试运行（原 0.2 H3）要在云端运行上做才有意义，移到本版本（2026-10-22）。
- **覆盖面**：总计划里欧美来源排在这一阶段（`docs/PLAN.md` 第 5 节）；日本的 e-Stat API 和几类命名文件（0.2 计划第 4 节写“放到 0.3 或之后”）一并做。

## 3. 目标（MAPLE 完成的标准）

1. **云端定时运行**：GitHub Actions 按来源各自的频率定时抓取、解析、建索引（含向量），结果写进 R2；同一时间只有一个写入者；一次运行失败不会留下半截状态。
2. **状态在 R2 上，可重建**：raw、各库（manifest、chunk、关键词、目录、变化）、观测值、向量都在 R2 上有一致的代次；下一次运行和本机都能从 R2 恢复，恢复后能还原任意一条出处。
3. **本机拉取**：`datumoj pull` 把 R2 上最新的完整代次拉到本机，MCP 照常在本机回答；本机的定时抓取和 Actions 不能同时写。
4. **一周试运行**：所有来源在 Actions 上连续跑一周，提醒和每周变化报告合理，短保留来源（JMA）没有时间缺口（原 0.2 H3）。
5. **欧美来源入库**：data.europa.eu、Eurostat、英德法荷四个开放数据门户、Federal Register、世界银行 WDI。
6. **日本来源入库**：e-Stat API（精选表）、国土数值信息、2024 经济普查、医疗开放数据、ABR 地址（各自的范围在 H2 定稿）。
7. **多语言检索**：英语和欧洲语言的问题也能检索到对应资料；关键词相关性门槛在这些语言上同样有效。
8. **评测**：新增欧美、日本新来源、多语言、跨国比较几类题，共 30 题以上；和 IVY、TACHIBANA 的题一起全部达标。
9. **真实问答验收**：在 Claude Code 里注册 MCP（本机拉取的数据），用日、中、英三种语言提问，回答带出处和断言级别。

## 4. 不做

- **部署到 Cloudflare Workers / Cron Triggers、D1**：运行环境定为 GitHub Actions；数据库不迁到 D1（ADR 0002：不把在线数据库文件放在对象存储上，本机或 Actions 上运行，代次备份到 R2）。
- **对外公开的查询服务**：R2 上的数据只给本项目的运行和本机拉取用，不开放公共访问。
- **需要 Key 的美国来源**：GovInfo、Data.gov（api.data.gov Key）等 Key 到位以后再排。
- **KKJ 采购公告**：仍不在本版本。
- **数据清理**：仍由另外的 batch 机制处理；R2 上的旧代次保留期由人另定，本版本不自动删除。
- **主动推送**（邮件、聊天通知）：提醒和报告仍只在命令行、管理页面和 R2 上的报告文件里。
- **中、俄、土、印等其他国家**：仍不做。
- **气象厅平年值、国土地理院标高**：不在本版本。

## 6. 设计上的新增内容

### 6.1 契约修订（先做，由人审查）
- **状态代次清单**（`StateGeneration`）：代次号、生成时间、写入者（Actions 运行号或本机）、各库副本的对象键和 SHA256、raw 前缀、向量模型和版本、向量覆盖（已建向量的块数和待建块数）、包含的来源及各自的最后成功运行。只有清单最后发布、全部副本都已上传的代次才是有效代次（ADR 0002）。
- **写入租约**：R2 上一个租约对象（持有者、取得时间、到期时间），用对象存储的条件写入（`If-None-Match` / `If-Match`）原子地取得、续期和释放；发布新代次时也用条件写入，只有代次号紧接着当前有效代次时才成功。
- **来源的同步频率**：`sources/*.yaml` 已有 `schedule`（如 `hourly`、`daily`），本版本明确它就是 Actions 上的抓取频率；需要时加上“状态上传频率”，不加就与抓取频率相同。
- 修订会影响已有代码，契约任务的 `unprotect` 要明确列出允许改的已有测试。

### 6.2 状态上 R2（ADR 0002 的实现）
- **一致的副本**：SQLite 用 backup API、DuckDB 用导出或停写后复制，不直接复制正在写的文件；同一代次里各库是同一时刻的状态。
- **上传和发布**：先上传副本，最后写代次清单；中途失败的代次不会成为恢复入口。
- **恢复**：恢复到新目录，校验 SHA256，抽样还原出处后再切换。
- **体积**：本机向量库现有 15G，先查是否是没压缩的历史版本；每次运行不应整份下载和上传。向量库有两种做法，由 A 线的第一个验证任务定：LanceDB 直接读写 R2 上的表（ADR 0002 说可行，需要对锁定版本做专项验证），或按来源分表、只拉当次要写的来源。SQLite 库体积（当前约 1.8G）也按同样思路评估是否要按来源拆分。

### 6.3 GitHub Actions 运行
- **工作流**：定时触发（例如每小时一次）加手动触发；每次运行算出到期的来源，只跑这些来源；`concurrency` 保证同一时间只有一个运行。
- **流程**：从 R2 恢复最新代次 → 抓取到期来源 → 解析和建索引（增量）→ 生成新代次上传 R2。
- **向量**：Actions 上装 Ollama 和 bge-m3（模型缓存），**只给新增的块建向量**；第一次全量在本机建好，作为第一个代次上传（H3）。
- **凭证**：只从 Actions secrets 读（`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、e-Stat appId），`R2_ENDPOINT` 和 bucket 名放 Actions variables；来自 fork 的 PR 拿不到这些。**仓库是公开的，Actions 日志也是公开的**：日志里不能出现凭证、个人信息和原始数据。
- **单写入者**：`concurrency` 只能串行化 Actions 自己的运行，挡不住本机。所以 Actions 和本机写入前都要先取得 R2 上的写入租约（6.1），拿不到就不写；发布代次用条件写入，检查和发布之间被别人抢先时发布失败、这一轮作废。租约到期前持有者要续期。`--force` 只用于接管已过期的租约（例如上一个运行崩溃），不能绕过一个仍有效的租约。Actions 接管某个来源后，本机对这个来源的定时抓取要停掉。

### 6.4 本机拉取
- `datumoj pull`：下载 R2 上最新的有效代次到本机（只下载有变化的部分），校验后切换；MCP 和 `datumoj search` 读本机副本。
- 拉取后本机的库是只读工作副本，回答里的数据截止时间写代次的生成时间。

### 6.5 监控和报告上云
- 运行记录、提醒和每周变化报告随代次进 R2；`datumoj schedule status` 和管理页面读本机拉下来的副本。
- Actions 运行本身失败（工作流失败、超时、被跳过）也成为提醒。定时触发在 Actions 上可能延迟或被跳过，监控按“预期频率内没有成功运行”提醒。

### 6.6 欧美来源
- **目录门户**：CKAN 系（英、德、荷）复用 IVY 的 CKAN 采集器，只加配置和必要的差异处理；data.gouv.fr（udata）和 data.europa.eu 各写一个适配器，产出同样的 `Dataset`。
- **统计**：Eurostat（SDMX）和 WDI 产出观测值，进 `query_sql`；查询结果必须保留 `obs_id`，才能生成逐行出处；单位、年份、地区编码原样记录，跨国比较时不自行换算货币。
- **Federal Register**：按文件（document number）抓全文，按节切块，locator 写节标题路径；按发布日期增量。

### 6.7 多语言检索
- 关键词索引现在用 FTS5 的 trigram 分词，对英语和欧洲语言也能工作，但相关性门槛（TACHIBANA-501）是在日语、中文问题上校准的，要在英语等语言上重新校准。
- 向量一侧 bge-m3 本身是多语言的，跨语言检索（用中文问欧盟数据）作为评测题覆盖。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 日本政府站点拒绝 Actions 的海外 IP | H3 先手动跑一次核对；不行的来源退回本机运行，或改用自托管 runner |
| Actions 定时触发延迟或被跳过（仓库 60 天不活动时定时会被停用） | 监控按“预期频率内没有成功运行”提醒；JMA 的缺口单独提醒 |
| 单次运行超过 6 小时、磁盘不够 | 每次只跑到期来源；向量增量；库按来源拆分（101 的结论）；首次全量在本机做 |
| Actions 上 CPU 建向量太慢 | 只给新块建向量；单次运行设上限，没建完的下次继续，不阻塞发布；代次清单记录向量覆盖，还没建向量的块照常能被关键词检索找到，`search_docs` 和 `datumoj pull` 在覆盖不全时注明“向量覆盖 x / y” |
| 两个写入者同时写，状态互相覆盖 | R2 写入租约 + 条件发布（`concurrency` 只管 Actions 内部）；代次清单记录写入者 |
| 中途失败留下半截代次 | 先传副本、最后发布清单；恢复只认已发布的代次 |
| 公开仓库的 Actions 日志泄露凭证或数据 | 日志只写计数和来源 ID；凭证只从 secrets 读；CI 的密钥扫描覆盖 |
| R2 费用 | 只存增量；不自动删除但记录体积；每周报告附上 R2 用量 |
| 欧美门户接口各不相同 | CKAN 系复用；非 CKAN 的各写适配器，产出同一个 `Dataset` |
| 跨国比较口径不一致，模型自行换算 | 回答规则禁止自行换算货币和口径；数值只从 `query_sql` 取 |
| 重做的任务丢失前几轮已确认的要求 | 审查确认的要求写进任务文件的固定条目 |

## 10. 和 TACHIBANA 的关系

- TACHIBANA（0.2）的开发已完成（PR #15），H4 真实问答验收待做；MAPLE 在其合并后的 `main` 上开发。IVY 和 TACHIBANA 的评测题和门槛继续作为回归基线。

## 11. 以后的方向（不在本版本，2026-10-22 记录）

- **单源失真验证**（https://plan.datumoj.com/verify/ ，30 例）和**多源融合分析**（https://plan.datumoj.com/cases/ ，100 例）是之后的方向：同一指标用 3 个以上独立来源交叉核对（例如官方 GDP 对夜光、贸易镜像、超额死亡），或把多个来源叠加回答一个问题。需要的来源以国际组织为主（IMF、OECD、世界银行、联合国各机构、WHO、BIS、ILO、UN COMTRADE、Copernicus 等），以及各国统计局。
- 本版本的 Eurostat、WDI 和跨国比较的回答规则（702）是这个方向的第一步：数值只从 `query_sql` 取、口径和单位原样记录、不自行换算，这些规则以后做融合和核对时同样适用。
- **法国政府开放数据（Hugging Face `AgentPublic/open_government`）**：https://huggingface.co/datasets/AgentPublic/open_government ，Parquet，约 2,400 万行，法语、英语等 20 多种语言的政府和监管文本（例如 AMF 的公告和招股书），数据集标注 Apache-2.0。**只记录，不抓取**；以后处理时再核对各子集原始来源的许可。补充说明见 https://plan.datumoj.com/hf-gov/ （Hugging Face 上 389 个 government 数据集的全量调查）：它约 380B tokens、16 个集合，是 LLM 训练语料，没有结构化字段和逐条出处，与 DATUMOJ 的“注册层 + 逐条证据链”不是一类东西。
- **DATUMOJ 自己发布数据集**（同一调查的建议）：把注册层（官方资源的机构、URL、许可、核查时间）和带逐条出处的垂直登记库发成数据集；许可和出处先行。HF 上日本政府数据目前为零。
