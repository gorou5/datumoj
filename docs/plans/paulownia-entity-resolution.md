# PAULOWNIA（桐）：法人实体解析试点

> 草案 v1（2026-11-11）。并行小版本之一，规则见 `docs/plans/parallel-versions.md`。任务编号 `DATUMOJ-PAULOWNIA-<序号>`，分支 `feature/paulownia`。
> 依据：计划站的研究计划「表記ゆれ：从文字差异到实体解析」v0.5（2026-11-02，https://datumoj.com/plan/hyoki-yure/ ），其第 8 节建议第一阶段做法人。

## 1. 一句话

把法人番号和政府采购公告接进资料库，建一层"记录 ↔ 实体"的关系，并做出第一个可评估的法人匹配基线：保留每个来源的原始表记，用证据判断两条记录是不是同一个法人。

## 2. 完成标准

1. **法人番号入库**：国税厅法人番号的全件数据（或试点范围内的子集）入库，保留商号、所在地、法人番号、变更履历（旧商号、迁址、合并）和来源快照。
2. **采购公告入库**：官公需情报门户 KKJ 按日期增量采集（0.1 起一直推迟的 `jp-kkj`），公告里的发注机关和事业者名称作为待匹配记录；担当者个人信息入库前脱敏。
3. **实体关系层**：新库保存关系 `CONFIRMED_SAME / PROBABLE_SAME / DIFFERENT / RELATED / HISTORICAL_SUCCESSOR / UNRESOLVED`，每条带证据、有效时间、来源记录引用和撤销状态；不覆盖原始记录，不另发"新身份"。
4. **匹配基线**：同一测试集上比较三种方法——精确匹配加规则标准化、字符串/读音/地址相似度、多字段打分；输出 Precision、Recall、错误合并率、待人工复核比例。
5. **评测集**：以法人番号为权威证据构造正样本、普通负样本、困难负样本（同名不同法人、同址不同法人）、不确定样本；按实体切分训练/测试，避免泄漏。
6. **查询入口**：工具层和 MCP 加一个只读工具，给出某条记录的实体关系和证据。

## 3. 不做

- 不处理自然人姓名和居民数据；采购公告里的个人信息只脱敏，不进实体层。
- 不训练大模型；第一版是规则和打分，模型方法留到有足够标注之后。
- 不把实体 ID 当法律身份凭证；不替代法人登记。
- 不做异体字映射工程本身，只把字形差异当一种证据。

## 4. 拥有的目录

- 新文件：`src/datumoj/rikolto/crawlers/houjin.py`、`crawlers/kkj.py`、`parsers/` 下对应解析器；
- 新子包 `src/datumoj/rikolto/entity/`（关系库、候选生成、匹配、评测）；
- 新来源 `sources/jp-houjin.yaml`、`sources/jp-kkj.yaml`；

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 法人番号全件数据体量大（数百万法人，待 H1 核实） | 先按试点地域取子集；R2 写入前给估算（并行规则第 3.4 节），等 KATABAMI 的闸门 |
| 错误合并 | 高风险结果进人工复核；关系可撤销并留审计 |
| KKJ 公告含个人信息 | 入库前脱敏，沿用 TACHIBANA 设计的 Redaction |
| 研究计划时间线（2027-02 原型） | 本版本只承诺第一个可评估基线；跨组织试点不在本版本 |
