# 并行小版本：清单与规则

> 草案 v1（2026-11-11）。从这一版起，0.4 之后的工作拆成多个**目标单一的小版本**，团队成员各自认领、同时开发；哪个先完成，哪个先合进 `main`。版本规则的总述见 `docs/PLAN.md` 第 8.4 节。

## 1. 为什么这样做

- 0.1–0.4 是一个版本接一个版本做，版本里的开发线互相等。
- 后面的工作大多互不依赖（容量治理、法人实体、国际来源、注册层发布、NAS 下游），拆开以后每个人可以从 `main` 拉一个分支独立做完，不用等别人。
- 每位成员本地同一时间只做一个版本；并行发生在成员之间。

## 3. 规则

### 3.1 分支与合并
1. 认领后从最新的 `main` 拉 `feature/<代号小写>`，比如 `feature/katabami`。
2. 版本内的任务只合进自己的特性分支。
3. 完成标准达到、人工验收通过后，向 `main` 提 PR。提 PR 前先把最新的 `main` 合进来，在合并后的代码上跑全量测试（`make check`，排除现存 xfail）。
4. 谁先通过谁先合并，不按代号顺序排队。
5. **需要真实云端验收的版本**（比如 KATABAMI 要在真实 R2 上清理）：特性分支不写 R2（第 3.4 节），所以分两步——
   - 离线验收（测试、回放、只读统计）通过后先合进 `main`，新的写入或删除行为默认关闭，或只在手动触发时运行；
   - 合并后从 `main` 手动触发做真实验收，通过后才发布（第 3.2 节）；不通过就在 `main` 上修，期间开关保持关闭。

### 3.2 版本号和 tag
- 任务编号用代号：`DATUMOJ-<代号>-<序号>`，号段沿用开发线（契约 001–009，A 1xx … G 7xx，集成 9xx）。
- **合并不等于发布。**版本号在**发布**时分配，按发布先后取下一个号（0.5、0.6 …）；发布时在当时的 `main` 最新提交上打 `v<版本>-<代号小写>`（检查点打 `-m<N>`）。tag 包含发布时 `main` 上已有的全部内容，发布说明写明本版本的范围。
- 发布条件：合进 `main`，并且人工验收（含第 3.1 节第 5 条的云端验收）通过。合并了但还没验收完的，版本表里写"已合并，待验收"，不占号。因为 tag 会带上 `main` 上的全部代码，**只要 `main` 上还有待验收的版本，就暂停一切发布**，直到它验收通过，或者在 `main` 上回退。所以合并后的云端验收要尽快做，不要拖。
- 已有编号的 0.3、0.4 先发布；0.4 发布之前，小版本可以合进 `main`，但不发布，等 0.4 发布后按验收完成的先后依次发布。
- 计划文件按代号命名，不带版本号；发布时在 `docs/PLAN.md` 第 8.2 节版本表里补上版本号。

### 3.3 避免冲突
- 每个版本的计划写明"拥有的目录"。新代码尽量放进新文件，比如新采集器放 `crawlers/<新文件>.py`，新来源放 `sources/<新 id>.yaml`。
- **共用文件**（`core/models.py`、`core/contracts.py`、注册表 schema、`pipeline.py`、`cli.py`、`wiring.py`、`pyproject.toml`、`uv.lock`）：
  - 改动要小，只加不改；
  - 要改契约（数据模型、接口、注册表字段）的，把契约修订做成版本里的第一个任务，单独先向 `main` 提 PR；合并后其他版本合入 `main` 再继续。
  - 加依赖要在 PR 里写明理由；`uv.lock` 冲突时以 `main` 为准重新锁定。
- 两个版本必须改同一处时，在本文件第 4 节登记，由先合并的一方负责合并后的协调。

### 3.4 云端与共享资源
- 定时抓取只从 `main` 运行。版本里的新来源合进 `main` 以后才上线，特性分支不写 R2。
- R2 是全账户共享的（#84：9 GB 上限，7 GB 起每次写入前报告总量，8.5 GB 冻结非必要写入，9 GB 停止全部写入）。任何版本要往 R2 写数据（包括一次性回填）之前，都要先在 PR 里给出估算增量。
- 需要 key 的来源：key 只放运行环境变量和 Actions secrets，任务文件里只写环境变量名。
- GitHub Actions 的并发组 `rikolto-cloud-run` 是共用的，新增云端作业要加入同一并发组（`cancel-in-progress: false`）。注意同一组默认只保留一个待运行位置，新排队的会顶掉原来排队的那个：新增作业要说明被顶掉时怎么补跑（例如下一轮定时自然补上，或手动重新触发），不要让验收或一次性回填静默丢失。

### 3.5 来源与许可
- 新来源先做来源核实（官方接口、覆盖范围、凭据、配额、robots、许可、云端模型条款，附官方 URL 和核对日期），写成 `docs/plans/<代号>-sources.md`，人确认后才写采集器。每个来源一节，固定写这几项：官方接口和文档 URL、覆盖范围（指标、地区、时间）、凭据和申请方式、配额与限速、robots、许可名称和链接、云端模型条款、核对日期、未确认事项。（PR #169 的 `docs/plans/0.4-wisteria-sources.md` 合并后可作为完整示例。）
- 许可没核实完的来源：`outflow: no_outflow`、`cloud_model_ok: false`。

### 3.6 每个版本的计划写什么
目标与完成标准、不做什么、拥有的目录、依赖与冲突点、任务草稿（编号、内容、依赖、审查方式）、人工步骤（H）、风险。任务文件在计划 PR 合并后由认领人写，按 `docs/PLANNING.md` 念给人确认。

## 5. 和 0.3、0.4 的关系

- 0.3 MAPLE 计划 2026-11-17 发布；0.4 WISTERIA 还在 `feature/0.4` 上，等国际来源定稿（PR #169）。
- 新的小版本都从 `main` 拉分支，不从 `feature/0.4` 拉。依赖 0.4 内容的（目前只有 AOI 会用到 0.4 的 Eltiro 缺口报告和观测值发布历史），等 0.4 合进 `main` 后再合并；开发可以先做。
