# BELLFLOWER（桔梗）：注册层发布为数据集

> 草案 v1（2026-11-11）。并行小版本之一，规则见 `docs/plans/parallel-versions.md`。任务编号 `DATUMOJ-BELLFLOWER-<序号>`，分支 `feature/bellflower`。
> 依据：计划站的「Hugging Face government 数据集全量调查」（2026-10-22，https://datumoj.com/plan/hf-gov/ ）。结论是注册表/目录方向在 HF 上是空白，建议"把注册层本身发成数据集"。

## 1. 一句话

把 DATUMOJ 的来源注册表（`sources/*.yaml` 导出的 `catalog/*.json`）和资源目录，连同逐条出处和许可，发布成一个有版本的公开数据集。只发我们有权发布的元数据，不发抓到的数据本身。

## 2. 完成标准

1. **数据集内容**：每个官方数据来源一行，字段包括机构、名称、URL、接口类型、国家/地区、覆盖场景、许可名称和链接、我们的核对日期、核实状态；另有一张"资源"表（如果 H1 确认 orbis 目录可以再发布）。
2. **出处字段**：每行带来源 URL、核对时间、数据发布时间（和核对时间分开）、生成规则的版本。
3. **格式**：Parquet 加 SQLite，各带 schema 说明；有稳定版本号，每次发布可复现（同样的输入生成同样的文件）。
4. **数据集卡片**：写明用途、字段、许可（发布物自身的许可和上游条款分开写）、局限，面向两类读者——LLM 构建者和研究者。
5. **生成命令**：`rikolto registry export`（或同等命令）离线生成发布物，CI 校验 schema；发布动作由人执行。

## 3. 不做

- 不发布抓取到的数据、文档正文或观测值；不发布许可不允许的上游内容。
- 不自动发布：上传到 HF 等平台由人操作，凭据不进仓库。

## 4. 拥有的目录

- `catalog/` 导出格式（TACHIBANA 起的注册层描述导出），新增 `src/datumoj/rikolto/registry_export.py`（或同名子包）；
- 数据集卡片放 `docs/datasets/`；
- 不改采集器。新来源各自往 `catalog/` 加 JSON，BELLFLOWER 只定义格式和导出。

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 上游目录的许可不允许再发布 | 资源表单独做（103），H1 不通过就只发我们自己写的来源表 |
| 注册表里有内部信息（key 的环境变量名、容量上限等） | 导出字段用白名单，不整份导出 yaml |
| 发布后内容过时 | 每行带核对日期；发布物带版本号，卡片写更新频率 |
