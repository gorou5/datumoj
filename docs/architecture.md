# 架构文档

## 1. 使命

连接世界各国及地区政府侧公开的数据，为用户定义的场景提供数据访问、
检索、处理、分析和自动化能力。**连接数据，而不是占有数据。**

## 2. 总体架构

```
                    ┌─────────────────────────────┐
                    │        用户定义场景           │
                    │  (分析/检索/自动化/可视化…)   │
                    └──────────────┬──────────────┘
                                   │ 统一调用标准
              ┌────────────────────┼────────────────────┐
              │                    │                    │
     ┌────────▼──────┐    ┌────────▼──────┐    ┌───────▼────────┐
     │  连接器/适配器  │    │ Skills/Agents │    │ MCP Servers /  │
     │  (官方API/下载) │    │  (工作流/工具) │    │ Workers/本地程序 │
     └────────┬──────┘    └────────┬──────┘    └───────┬────────┘
              │  统一描述标准       │                   │
              └────────────────────┼───────────────────┘
                                   │ 统一证据标准
                    ┌──────────────▼──────────────┐
                    │   各国政府官方数据源        │
                    │ (API / 下载接口 / 公开页面) │
                    └───────────────────────────┘
```

- **模块**（连接器、Skill、Agent、MCP 工具、Worker……）是基本组成单位，
  各自独立、低耦合，通过**统一描述**被发现、通过**统一调用**被组合。
- **数据**始终指向官方来源；项目本身默认不囤积原始数据副本。
- **证据链**伴随每一次数据流动：谁、在何时、从哪个官方来源、取了哪条记录。

## 3. 三个统一标准（互操作基础）

| 标准 | 解决的问题 | 规范位置 |
|---|---|---|
| 统一描述标准 | 模块能被发现：这是什么、解决什么问题、怎么用 | `schemas/registry/module.schema.json`、`schemas/registry/data-source.schema.json` |
| 统一调用标准 | 模块能组合：输入输出、错误、超时、版本 | `docs/interoperability.md` §2 |
| 统一证据标准 | 数据可追溯：来源、记录 ID、采集时间、断言级别 | `docs/interoperability.md` §3 |

详细定义见 [interoperability.md](interoperability.md)。先用一个最小真实场景
（`examples/data-sources/jp-nta-houjin-bangou.json`：日本国税厅法人番号公表サイト）
验证标准有效，再演进。

## 4. 运行环境与 Cloudflare 原则

云端自动化**优先**考虑 Cloudflare（Workers / Cron Triggers / Queues /
R2 / D1 / Pages / Workers AI），但**不强行**使用：

- 不要为了用 R2 而存数据：R2 只在"确实需要保存文件/对象"时用；
  Worker 能用 R2 Bucket Binding 就不要把 S3 密钥发给 Worker。
- 不要假设所有结构化数据都进 D1；元数据、索引、任务状态按需选择。
- 核心业务逻辑与平台解耦，平台相关能力放入独立适配层；
  同一个连接器应能被 Worker、本地 Agent、MCP 多种方式调用。
- 交付物也可以只跑在用户本地、用户 AI agent 中，或部署到其他合法环境；
  必须诚实声明运行环境限制。

## 5. 数据策略（不搬运工）

默认**直接查询**官方数据源。仅在必要时保存副本：

- 必须暂存原始文件才能解析；增量处理需要的状态；
- 官方接口不稳定、在许可允许范围内的缓存；
- 用户明确要求保存查询结果；审计/可恢复处理需要的记录。

优先保存**元数据、索引、任务状态、来源引用**，而非原始数据全文。

Rikolto 保存原始快照，属于上面"审计/可恢复处理"的情形：问答要可复现、出处要能还原到原文。具体取舍见 `docs/PLAN.md` §1.1。
每种缓存/存储必须声明：目的、保留期限、清理策略。
对每个数据源说明：是否直接查询 / 是否缓存 / 是否允许再分发 /
频率限制 / 署名要求 / 更新与失效机制（见 `docs/data-sources.md`）。

**禁止**：把"可公开访问"等同于"可无限制批量复制/长期保存/再分发"；
来源不可用时用未经验证的替代数据冒充。

## 6. 模块组织

- 按**国家/机构/数据类型/场景**独立贡献，一个目录一个职责。
- 不要把所有功能塞进一个大应用；也不要把简单功能过度拆分。
- `connectors/`、`skills/`、`agents/`、`mcp/`、`workers/` 等目录
  **在第一个真实模块落地时创建**，不预建空目录。
- 公共接口遵循语义化版本；破坏性变更必须走 PR 说明并检查调用方。

## 7. 协作与治理

- 分支 + PR + CI + 人类审查（见 CONTRIBUTING.md）；AI 产出同样要审。
- 正式部署走统一 CI/CD；生产凭证永不进仓库（见 SECURITY.md）。
- 许可证待定（候选 MIT / Apache-2.0），确定前不擅自添加 LICENSE 文件。
