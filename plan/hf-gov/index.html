Hugging Face 上的「government」数据集：389 个全量调查

datumoj 要做自己的数据集，先看清这片地里已经有什么：谁在做政府数据、做成了什么样、热度在哪、以及——有没有人已经做过 datumoj 想做的事。

调查日期：2026-10-22 ｜ 数据来源：Hugging Face 官方 API 以 search=government 全量拉取（与网站搜索页显示的 389 个一致），含每个数据集的作者、近 30 天下载、累计点赞、许可证、语言、规模与说明全文 ｜ 原始数据与分析脚本同目录存档（datasets.json、analyze.py），口径可复现。

结论先行

  • 389 个里，245 个（63%）是同一个「工厂」的产品。Electric Sheep 的三个地区账号（africa/asia/europe）把世界银行、UN SDG、Our World in Data、FAOSTAT 的指标逐条切开——只要指标名里带 government 就生成一个小数据集。它们近 30 天合计只有 2,591 次下载、0 个赞，是这片地里的“背景噪音”，不是竞争者。
  • 近 30 天下载集中在“给机器吃”的数据上。近 30 天下载共 29,126 次，前 10 个数据集占 78.7%。按近 30 天下载排名第一的（12,358 次）是智源 BAAI 的 LLM 预训练语料 IndustryCorpus2 里“时政与行政”一个切分——government 在这里只是语料的一个行业分类。
  • 赞数之王是认真做溯源的单国文档库。ankitjh4/bharat-government-documents（印度政府公开文档 64,964 篇，每篇带源 URL、抓取时间、抽取质量、规则版本）拿到 65 个赞——是全场赞数的 59%。下载拼规模，点赞拼手艺。
  • 真·同题材的大玩家只有一个：AgentPublic/open_government。约 380B tokens、16 个集合、23 种欧洲语言，汇编美国、法国、欧盟与国际组织的开放数据做 LLM 语料，自称“最大的政府文本与数据汇编”。但它做的是训练语料，不是可查询、带出处的结构化数据。
  • datumoj 想做的两件事，Hugging Face 上都还没有人做：① 跨国政府开放数据的注册表/目录做成数据集（全场只有 3 个“目录·清单型”，包括美国政府出版物 URL 目录，近 30 天下载 8 次）；② 以官方来源为准、逐条带出处的垂直领域登记库（如 tel.datumoj.com 的电话号码库）——方法论上唯一的近亲是 Bharat Guide，而它做的是文档、不是登记数据。
  • 纪律就是差异化空间：24% 的数据集没写许可证（法律上等于不可用），77 个连 40 字说明都写不满，358 个（92%）零赞。把许可证、出处、更新时间写清楚，本身就是这片地里的稀缺品。

纪律与质量：这片地的软肋

  • 许可证缺失 95 个（24%），另有 81 个只写含糊的 “other”。没有许可证的数据集，任何人都不能合法再分发——做数据集的人最常省的恰是最关键的一步。
  • 说明贫瘠：77 个数据集的说明不足 40 字；来源、更新时间、字段含义普遍缺失。工厂切片虽有模板化说明，但每集只是同一段话换指标名。
  • 重复与一次性：阿曼统计、泰米尔医疗设施都出现同题重复上传；独立发布者大多传完即走，无版本维护。
  • “官方”含量低：几乎没有政府机构本人在 HF 发布；数据的权威性靠搬运者自律，普遍没有逐条出处。

与 datumoj 的关系：谁做过类似的事？

问：有人做过“连接各国政府公开数据”的数据集吗？

  • 注册表/目录方向：没有。最接近的是 alea-institute 的美国政府出版物 URL 目录（26 万条、近 30 天下载 8 次）和政府 GitHub 仓库清单——都是单国、单用途的清单。datumoj 在 orbis 层做的“471 个官方资源按场景注册”这种跨国注册表，在 HF 上不存在对应物。
  • 全球汇编方向：只有语料形态。AgentPublic/open_government 是唯一以“全球政府数据”为旗号的，但产品是 LLM 训练文本：无结构化字段、无逐条出处核查、不能当登记库查询。datumoj 的“注册层 + 逐条证据链”是另一种物种。
  • 垂直登记库方向：没有同类。以 tel.datumoj.com（日本电话号码：总务省官方指定数据为基础、逐条可溯）为代表的垂直打法，在这 389 个里找不到对应物；方法论近亲只有 Bharat Guide 的文档溯源纪律。
  • 日本方向：完全空白。日语数据集 0 个，日本政府数据 0 个。datumoj 的日本垂直（tel）在这里是无竞争区。

对 datumoj 做数据集的 5 条建议

  1. 把注册层本身发成数据集。把 orbis 的官方资源注册表（机构、URL、场景、许可、核查时间）以 parquet+SQLite 发布——这是全场确认的空白，且与 Bharat 的成功公式同构：注册表即产品。
  2. 逐条溯源写进 schema。源 URL、抓取时间、数据发布时间（与抓取时间分开）、规则版本、许可——Bharat 拿到 65 赞的字段，正是 datumoj 证据标准（AGENTS.md §3.3）已经在做的事，把它变成数据集的卖点。
  3. 许可证先行。每份发布明确 CC-BY-4.0 或 CC0（视上游许可），并在卡片里写清上游条款。24% 的同行在这里裸奔。
  4. 垂直深度优先于横向广度。工厂模式（245 个浅切片、0 赞）是反面教材；ZipLime（单题材做到全量+时点语义）和 Bharat（单国文档做到逐篇溯源）证明深度才有下载与赞。
  5. 同时服务两类已验证的读者：LLM 构建者（要语料规模、去重与规范化说明）与量化研究者（要时点语义、全量覆盖、稳定版本）。数据集卡片按这两类读者写。

方法与口径

本页数字来自 2026-10-22 通过 Hugging Face API（GET /api/datasets?search=government&limit=1000&full=true）的一次全量拉取，共 389 条，与网站搜索页计数一致；原始响应（datasets.json，692KB）与统计脚本（analyze.py）与本页同目录存档，可复跑复核。注意三点口径：① 关键词是英文 government，靠标题/说明/标签命中，非英语国家的政府数据集会被系统性漏掉（例如各国以本国语言命名的数据集）——本调查反映的是“HF 上以 government 为旗的生态”，不是全球政府数据的全集；② 主题分类为规则计分（推导），个别数据集可能误分，头部数据集的定性描述均已逐个打开核对（已证明）；③ 下载采用 Hugging Face API 的 downloads 字段，表示拉取时点之前近 30 天的下载次数；总量、占比与排名均使用这一窗口，不代表历史累计下载或全时期热度。点赞为拉取时点的累计值。两者都会继续变化（官方字段说明）。Electric Sheep 三个账号是否同一运营方，依据其命名、模板与指标来源的一致性推断（推导，未经该方确认）。
