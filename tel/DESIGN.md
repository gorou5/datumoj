# tel.datumoj.com 数据库设计 v1

日期：2026-10-22　依据：同日深度调研（jp-phone-lookup-pseo-architecture）+ 第三方有害数据源核查（本文 §5 的来源均于 2026-10-22 实查）

> **v1.2 修订（2026-10-22，用户定版，现行）**：① 数据基础以**号码计划的格式规则计算**为准（号种/位数/切分/前缀带均为规则生成），只有区号/MA 这类指定表本身即表格形态的数据才作参考表存入；② 数据库为**独立的一个 D1 数据库 `tel_datumoj`**，库内**表名全部语义化、不用缩写不用前缀**（prefecture / line_type / carrier / area_code / charge_area / number_block_allocation / business_registration / user_report / third_party_source / third_party_flag / government_agency / government_number），按 DBA 标准范式建模（MA 与区号一对一，都道府县建参考表），5 个视图供拼接管线使用（v_area_summary / v_charge_area_detail / v_number_block_detail / v_third_party_flag_detail / v_government_number_detail）；government_number 用代理键 + UNIQUE(number, agency_id)，因为一个代表号码可被多个机构共用（如 03-5253-5111 为总务省与消防厅共用）；③ 政府机构号码库只收官方页面实际刊载并逐条核验的号码，命中即 Tier 1 并在号码页展示「政府機関」区块；④ 只用免费公开资源，不做任何商务询价（トビラ等授权库仅登记在 third_party_source 备用，不接入）；⑤ 首页为 Google 式极简：日本电话号码结构完全解构 SVG 一张 + 搜索框一个；⑥ 11 位 0 开头号码全兜底：按前三位判番号带，未分配/位数不符出富内容 404 页。实现见仓库 `tel/`（Cloudflare Worker + D1 `tel_datumoj`，migrations 0001 建表 → 0002 语义改名 → 0003 政府号码键修复，为现行 schema）。

## 0. 设计原则

1. **不存单号行**。日本在用号码约 2.49 亿，但号码计划的全部事实都挂在「区段」上：总务省按段指定事业者、NTT 按区号+局番划分 MA。主数据只存区段（数万行），单号页面在访问时拼接生成、进边缘缓存。
2. **页面 = 分表组合**。一个号码页的每个字段都来自某张分表或某个覆盖层，拼接管线见 §3。分表更新，全部相关页面自动跟着变（缓存按字段来源设 TTL）。
3. **三层分离**：主数据层（官方号码计划，客观事实）／覆盖层（企业登记、用户报告，我方运营）／第三方有害层（外部可信来源的标记，只镜像+引用，我方不自判）。三层在页面上分区呈现，不混排、不合并结论。
4. **索引层级由拼接结果计算**（§6），不人工维护。

## 1. 主数据分表（号码计划层）

| 表 | 内容 | 主键/键 | 规模（估） | 来源与更新 |
|---|---|---|---|---|
| `ref_line_type` 号种表 | 号种定义：固定 0AB-J、050 IP、070/080/090 移动、0120/0800 免费、0570 ナビダイヤル、0180、0990 等；每种含总位数、切分规则、可携性、说明文 | `code` | ~15 行 | 总务省电气通信编号计划；人工维护 |
| `ref_prefecture` | 47 都道府县 | `code` | 47 行 | 静态 |
| `ref_carrier` 事业者表 | 割当事业者：名称、类别（NTT东西/移动キャリア/050事业者等）、官网 | `carrier_id` | 数百行 | 总务省指定数据汇入 |
| `ref_area_code` 区号表 | 市外局番 → 都道府县、代表地域名、区号位数、启用年代 | `area_code` | ~数百行 | 总务省/NTT 公开资料 |
| `ref_ma` MA 表 | 561 个 MA（单位料金区域）：名称、所属 NTT 东/西、包含市区町村 | `ma_id` | 561 行 | NTT 东/西 MA 表 PDF 解析 |
| `ref_ma_range` | 区号 × 市内局番范围 → MA（一区号可跨多 MA，靠局番段区分） | (`area_code`, `exchange_from`, `exchange_to`) | 数千行 | 同上 |
| `alloc_block` **区段分配表（核心）** | 号段 → 割当事业者：号种、前缀起止、指定年月日（＝该段「启用时间」）、状态（指定済/未指定/廃止） | (`line_type`, `prefix_from`, `prefix_to`) | 数万行 | 总务省别纸 PDF 解析（无 CSV/API，需建解析管线）；移动 070/080/090 按前 6–7 位分段；固定按区号+局番段 |

查询方式：**最长前缀匹配**——给定号码，在 `alloc_block` 里找包含它的最窄区段，即得割当事业者与指定日。

## 2. 号码标准化与切分

拼接前先把任意输入归一化为纯数字国内格式：

- 去除连字符/空格/全角字符；`+81` 开头 → 首位补 `0`；站内搜索、URL、库内键一律用此格式（连字符版仅作页面展示文本，不建独立页）。
- 按号种切分展示：固定电话＝市外局番（2–5 位可变）＋市内局番＋加入者番号（末 4 位）；手机/050＝3-4-4；0120/0800＝4-3-3；0570＝4-3-3。
- 切分规则存 `ref_line_type` 与 `ref_area_code`（区号位数决定固定电话切分点），不写死在代码里。

## 3. 页面拼接管线（组合生成）

请求一个号码页时依次执行（命中边缘缓存则跳过）：

1. **归一化** → 纯数字号码；格式非法 → 404。
2. **分类** → 查 `ref_line_type` 定号种；该号种未分配任何区段 → 真 404（Tier 3）。
3. **区段匹配** → `alloc_block` 最长前缀匹配：得割当事业者、指定年月、区段状态；未命中任何已指定区段 → 404。
4. **地域解析**（固定电话）→ `ref_area_code` 定都道府县；再以区号+局番查 `ref_ma_range` → MA 名称与包含市区町村。手机/050 无地域（页面明示「携帯・IP は地域を特定できない」）。
5. **覆盖层拼接** → 查 `ov_business`（企业登记）、`ov_report`（用户报告汇总）（§4）。
6. **第三方层拼接** → 查 `tp_flag`（§5）：命中则生成「第三方标记」区块。
7. **层级判定** → 按 §6 规则计算 Tier，决定 index/noindex 与是否进 sitemap。
8. **渲染 + 缓存** → 页面区块顺序：号码与切分图 → 基本事实（号种/地域/MA/割当事业者/指定年月＋可携性注记）→ 第三方标记（有才出现）→ 企业信息（有才出现）→ 用户报告（有才出现）→ 相邻号码与同区段链接 → 面包屑（号种 > 区号 > MA/局番 > 号码）。

字段溯源示例（每个字段都能回答「从哪张表来」）：

| 页面字段 | 来源 |
|---|---|
| 固定/移动/IP 等号种 | `ref_line_type` |
| 番号の切分表示 | `ref_line_type` + `ref_area_code` |
| 都道府县・地域 | `ref_area_code` |
| MA（単位料金区域） | `ref_ma_range` → `ref_ma` |
| 割当事業者 | `alloc_block` → `ref_carrier` |
| 启用时间 | `alloc_block.designated_on`（区段指定日，页面注明是区段级而非单号级） |
| 当前事业者 | **不提供**——号码可携（移动 NP 累计逾 1 亿次）使初始分配≠现状，页面只标「割当事業者」并附可携注记 |
| 企业名/地址 | `ov_business`（带登记来源） |
| 有害标记 | `tp_flag`（带第三方来源与原文链接，§5） |

## 4. 覆盖层（我方运营数据）

| 表 | 内容 | 要点 |
|---|---|---|
| `ov_business` 企业登记 | 号码 → 企业名、地址、业种、登记来源、核验状态 | 来源候选：公开企业名录、用户提交+人工核验；トビラ/iタウンページ 约 600 万件事业者数据是授权制，一期不含，列入合作目标 |
| `ov_report` 用户报告 | 号码、报告类别（詐欺疑い/迷惑/営業/無言等）、本文、时间、审核状态 | UGC 必须先审后显；页面只展示通过审核的汇总（件数+最新时间+代表性文本），原始报告不全量公开 |

## 5. 第三方有害库（辅助验证层）

### 5.1 定位与铁律

- 我方**不自己判定**任何号码有害；只镜像可信第三方的公开判定，并**逐条带来源**：来源机构、标记原文、公表日、原文链接、我方抓取日。
- 页面呈现文案模板：「{来源机构}：该号码被列为{标记类型}（{公表日} 公表）」＋原文链接。多个来源命中时**并列展示，不合并成一个结论分**。
- **伪装警告必配**：诈骗常用「発信者番号偽装」冒充真实号码（含警察署末尾 0110 的号码）。凡命中诈欺类标记，区块内固定附注：「来电显示可被伪装，该号码的登记持有者可能与诈骗行为无关。」
- 无标记时显示「目前未发现第三方标记」——**绝不显示「安全」**（名单未收录≠安全，金融庁对自家名单亦有此声明）。
- 每条标记设 `last_verified`，定期回源复核；来源删除/更正则同步更新或下架。被标记号码的持有者可走申诉通道人工复核。

### 5.2 表结构

| 表 | 字段要点 |
|---|---|
| `tp_source` 来源注册表 | `source_id`、机构名、来源名、入口 URL、发布方类型（官公庁/警察/商业DB/UGC）、可信等级 A/B/C、数据形式（Excel/PDF/HTML/授权Feed）、是否含单号、抓取方式与频率、利用条件备注、最近抓取日 |

### 5.4 页面呈现规范

- 区块标题：「第三方标记（辅助验证）」，与我方覆盖层的「用户报告」严格分开——前者是外部机构的判定，后者是本站用户投稿，视觉与措辞都不得混同。
- 每个标记徽章带可信等级：A＝官方/官方授权渠道、B＝官方公开名单、C＝公开情报参考。C 级永不单独触发 Tier 1 升层（§6），A/B 级可。
- 区块底部固定一行：数据来源与更新时间、申诉入口。

## 5.5 政府机构号码库（官方号码）

| 表 | 字段要点 |
|---|---|
| `government_agency` 政府机构表 | 正式名称、简称、类别（省/庁/委員会/府/院等）、官网 |
| `government_number` 政府号码表 | 归一化号码（唯一）、机构 FK、号码类别（代表/相談窓口/其他）、用途说明（按官方页面原文）、出处 URL（刊载该号码的官方页面）、核验日期 |

规则：只收在官方页面（go.jp 等）上亲眼核验到的号码，未核验到的机构宁缺毋滥、绝不凭记忆补；每条号码必带出处页与核验日，定期回源复核。页面呈现：号码页顶部「政府機関」徽章区块（机构名＋类别＋出处链接），并固定附伪装警告（政府号码正是诈骗伪装的重灾区）；机构目录页 `/gov` 汇总全部机构与号码；政府号码一律 Tier 1 并进入 sitemap。

## 6. 索引层级（拼接时计算）

| Tier | 条件（拼接结果） | 索引策略 |
|---|---|---|
| 0 枢纽页 | 都道府县/MA/区号/前缀段聚合页 | index，进 sitemap |
| 1 | 有企业登记，或有已审用户报告，或命中 A/B 级第三方标记 | index，进分片 sitemap；按前缀分批放量，盯 GSC 收录率 |
| 2 | 已分配区段内但无任何覆盖数据 | 可访问，**noindex**；覆盖数据一到自动升 Tier 1 |
| 3 | 未分配/格式非法 | 真 404，不生成页面 |

## 7. 存储与规模

- 主数据 7 张表合计约数万行 → Cloudflare D1 单库足够；`tp_flag` 初期量级取决于合作接入（金融庁备考号码+名称联动为百量级；トビラ接入后另议）。
- 全部页面由同一个 Cloudflare Worker 运行时从 D1 拼接渲染（SSR），渲染结果进边缘缓存：枢纽页 `s-maxage=86400`、号码页 `s-maxage=604800`（长 TTL，字段来源变更时按区段批量失效）。边缘命中时即静态响应，**视作等效 SSG**。
- **架构定版注记（v1.3，2026-10-23，用户决定）**：早期设计曾写「枢纽页 SSG 走 Pages」，实现未采用、现改文档对齐实现。理由：枢纽页内容随 D1 数据变化，预生成静态化要多维护一条构建发布链路；Worker SSR＋长 TTL 边缘缓存在效果上等价（回源才渲染），且与号码页同一条拼接管线。不再另建 Pages 静态站。
- 全部表带 `source` 与 `updated_at`，任何页面字段可回溯到来源与日期——与 datumoj「只用官方数据库」的一贯规矩一致。

## v2.0 追記（2026-10-25、オーナー決定）：年度別「番号基礎表」

- **番号基礎表**：一度でも引かれた番号は「既知」として、その事実スナップショットを
  年度別テーブル `number_record_<初回照会年>` に1行で保持する（§6 の Tier 判定材料・
  事業者・指定日・市外局番・都道府県・MA・政府機関名に加え、`view_count` /
  `comment_count` のカウンタと `snapshot_version` を同居させる）。
- **照会経路**：番号ページは年度テーブルを新しい年から主キーで探査し、ヒットすれば
  スナップショットから描画する（上書き情報＝政府詳細・事業者登録・利用者報告・
  第三者標識はその場で小さく再読込し Tier を再計算）。未ヒット時のみ従来の拼接
  （区画探针）を行い、結果を今年のテーブルへ落とす（「引いたら1行落とす」）。
  未指定番号の列挙拼接はしない——3億件の列挙に意味はなく、照会された番号だけが基礎表になる。
- **スナップショットの鮮度**：公的指定データの再取込や拼接規則の変更時は
  `site_meta.snapshot_version` を進める。旧バージョンの行は次回照会時に再拼接して更新される。
- **表に入れないもの**：FAQ（よくある質問）・号種の通俗解説などのテンプレート文面は
  保存しない。表は「その番号が何か」の事実だけを持ち、見せ方は描画時にテンプレートが決める。
  FAQ は番号ページの**最後**のセクションとして描画する（オーナー決定 2026-10-25）。
- **第三者標識の表示**：番号の直下に**徽章（バッジ）**で級別色分け表示し、出典付きの
  詳細カードは従来どおり併記する（オーナー決定 2026-10-25）。
- **コメント**：本体は専用テーブル `number_comment`（従来どおり・年度分割しない）。
  件数だけ基礎表の行に冗長保持する。旧 `number_view` は基礎表へ移行し、参照のみ残す。
